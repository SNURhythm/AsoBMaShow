# Broad performance investigation — 2026-10-28

Baseline: `cb32aeca493445a783d3d24e540f70bee3f54663`. Repository unchanged. This was an investigation, not an implementation or device-latency diagnosis.

## Priorities

1. **Built-in MainMenu selection restoration under non-default sorting.** `src/repositories/ChartRepositoryQueries.cpp:2998` / non-default branch at 3014 loads every matching `ChartMetaRecord`, then finds one path. `MainMenuScene.cpp:3769` can invoke it separately for the prior top and selected items when their preferred indices no longer match. Actual desktop probe: 100,000 distinct matching synthetic charts, target at index zero, title/difficulty sorting: 528–544 ms and exactly 100,000 rich rows per lookup. At 5,000 rows: 22–25 ms. A narrow rank/path query should avoid rich-record hydration, though arbitrary sorting can still require a scan/sort. Preserve complete filter/order/tie/NULL and score semantics. Default sort has a separate count/rank path and is not this defect.

2. **Built-in MainMenu random-category preparation on reload.** `MainMenuScene.cpp:3715` calls `RandomChartMetaIndices`; `ChartRepositoryQueries.cpp:2094` performs ordered full-result reservoir sampling. `MainMenuLibrary.cpp:139` only consumes whether each index is negative, discarding the sampled indices. Search, folder and sort changes can run this synchronous path. Actual desktop probe: 100,000 matching rows, 203–228 ms, exactly 100,000 row steps, one SQL sort. At 5,000 rows: 6.7–7.4 ms. Separate category existence from actual selection, cache with membership/score revisions, skip sort-only invalidation, and stop an unordered scan when all category thresholds are known. An absent category can still require a full membership pass; this is not a guaranteed constant-time fix. Keep uniform sampling on actual activation.

3. **Music-player rate-slider persistence.** `MusicPlayerScene.cpp:1846` wires changed values directly to `setPlaybackRate`; `SnappedSlider.cpp:288` calls that callback for each changed snapped value during drag. The control uses 5-percentage-point steps (`MusicPlayerScene.cpp:4044`), not 1-point steps. `setPlaybackRate` synchronously calls `context.saveSettings()` at 3990. `context.h:1557` calls `saveActiveSettingsAndWait`; `ProfileSettingsPersistenceCoordinator.cpp:845` waits for the whole save. `processFullSave` calls `AppSettingsStore::Save`, which serializes versioned JSON and invokes atomic file/backup persistence including `fsync` (`AtomicFile.cpp:106`). Thus a drag can block the UI repeatedly on durable saves despite the separate persistence worker. Preserve live playback feedback, but coalesce persistence/defer the durable save to interaction completion with lifecycle/profile-switch handling. This source-confirmed I/O pattern is unmeasured; do not claim a measured slider hitch or weaken durability globally.

## Clear repeated work, lower current priority

- **HCN integration scans all HCN heads in non-LR2 gameplay.** `GameplaySimulation.cpp:896` makes four passes through all chart HCN heads even in an interval with none active. The gameplay worker normally wakes on input or a 1 ms timeout. The production `advanceTo` probe below confirms scaling, but the absolute desktop cost is modest: median 5.72 microseconds/advance for 1,000 future HCN pairs and 28.74 microseconds for 5,000, versus about 0.06 microseconds with equally many future ordinary CN pairs. At 1,000 advances/second those are approximately 0.57% and 2.87% of one core, respectively, not device measurements or deadline misses. An active-set/cursor optimization is plausible but must preserve HCN gauge threshold, early-release, chronological/note-ID ordering, terminal failure and catch-up semantics. Keep below the measured UI stalls unless low-end-device profiling says otherwise.
- **Recycler retained rows are laid out/copied again on every scroll offset change.** `RecyclerView.h:752–761` translates, unconditionally publishes layout for every retained row and copies each record into new containers, even with unchanged visible indices/content/dimensions. `View.cpp:851` recursively republishes descendant geometry and `onLayout`. A same-range scrolling path can reduce work. Cost is bounded by visible rows/descendants; no timing or allocation count was measured. Preserve width-before-bind behavior, dirty layout state and hit testing.
- **Custom music-select skins duplicate bar planning and warm atlas checks.** `MusicSelectSkinSession.cpp:87,1025` builds plans to gather title strings and repeatedly checks UTF-8/glyph/kerning residency; `Skin2DRenderer.cpp:3569` plans again during drawing. Actual glyph rasterization is already asynchronous and only triggered for missing content. Successful residency checks can likely be cached by exact string/atlas generation. Sharing plans requires caution because Lua/callback phases differ; a title-only collector may be safer. Visible-bar bounded and unmeasured, so profile before implementation.

## Measurement method and limits

Machine: Apple M1 Pro, macOS arm64. The temporary probes use real current production code linked from existing native-test objects (`-O1`, debug assertions/debug configuration), not a reimplementation. Inspected `GameplaySimulation`, `GameplayDefinition`, `ChartRepositoryQueries`, and SQLite compile commands/object timestamps. No production translation units or build outputs were replaced. No full application build or test suite was needed because source did not change.

Library probe reuses the existing `chart_selector_query_tests.cpp` fixture. It creates temporary databases with 5,000/100,000 rows, makes SHA-256 identity unique per row, sets nullable text fields to empty values, uses empty score caches, and calls actual Session APIs. Each sort gets three untraced timing trials, followed by a separate SQLite trace for row/sort/VM counts. Connections and OS data are warm after fixture creation/first-page setup. Title/difficulty probes target the first actual row. SQL trace confirms all 100,000 matching rows are materialized for those lookups. These times include the complete API call and destruction of temporary result records; they are not predictions of an optimized replacement or release-device behavior. The paged query itself still takes 83–89 ms in this large synthetic setup; eliminating the two identified costs will not make total reload time zero.

HCN probe builds charts with 10, 100, 1,000 and 5,000 future long-note pairs and compares CN versus HCN. The first note starts at 20 seconds. It invokes real `GameplaySimulation::advanceTo` at increasing 1 ms timestamps for 10,000 calls over the preceding 10 seconds, with three fresh simulations per size/type. No note becomes active, no gameplay worker is scheduled, and setup is excluded from timing. This isolates unnecessary future-HCN traversal; it does not benchmark active gameplay, tails, audio, power or mobile CPU scheduling. Small-count trials show warm-up noise; only the larger stable observations are used for ranking.

## Implemented follow-ups

The authorized follow-up implements all six findings in five coordinated changes:

- Non-default selected-chart lookup streams only normalized paths while retaining the exact query ordering and missing-entry positions. A 100,000-chart title lookup at index zero now takes about 154–164 ms in repeated probes versus the original 528–544 ms rich-row path. Final late/missing lookups take 224–231 ms. SQLite can still sort the entire candidate set; zero full chart records are materialized and retained C++ row state is bounded.
- Random category display now asks for availability rather than sampling a random result it discards. The unordered availability query has no outer sort and stops once thresholds are met. At 100,000 charts a mixed-category fixture reads two rows in 0.08–0.19 ms; proving Failed absent still reads all candidates in 127–130 ms. Actual activation retains fresh reservoir sampling and its uniform distribution. A single membership/revision cache reuses availability for sort-only reloads and invalidates for library, score, profile and query changes.
- Playback-rate feedback stays live while durable persistence occurs once per changed gesture. Completion, pointer cancellation, scene exits and application-background notification flush pending values. Profile ownership and error diagnostics remain guarded; background handling avoids rendering/resource work during a pending iOS frame.
- Non-LR2 HCN interval integration admits and expires eligible authored intervals instead of scanning every chart head repeatedly. In the same all-future production `advanceTo` probe, 1,000/5,000 heads changed from approximately 5.72/28.74 µs per advance to 0.24/0.16 µs. The post-change result has no chart-count trend at this scale; timing noise dominates. Existing LR2 behavior and strict tick ordering/thresholds are retained.
- Retained recycler motion avoids repeated record/container rebuilding, binding and recursive layout publication for unchanged rows. The structural fixture's sixteen fractional movements across three five-node rows produce zero item copies, bindings and layout callbacks. Dirty, externally calculated unpublished geometry and callback-driven raw Yoga changes still publish, including callbacks that finish a raw Yoga calculation before the movement ends. Coordinate translation, publication validation and Yoga's cached root calculation remain necessary work; no FPS gain is claimed.
- Music-select preparation gathers only title requirements and caches successful exact-string/atlas-generation residency checks within bounded storage. The actual session test verifies revalidation after full/metrics-only patches and no extra residency scans across 100 subsequent warm frames. Lua phases and draw-time animated geometry remain intact.

New gameplay-rendering candidates and measured component costs are recorded separately in [the rendering audit](2026-10-28-gameplay-rendering-audit.md). They have not been implemented by this follow-up.
