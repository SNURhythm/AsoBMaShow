# Selectable LR2 and Beatoraja Rulesets Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a per-profile LR2/Beatoraja ruleset selector with LR2 as the default, implement source-compatible LR2 judgment and gauge behavior, preserve current gameplay as Beatoraja, and allow Bokutachi submission only for attempts that carry canonical LR2 proof.

**Architecture:** A stable `GameplayRuleset` identity selects one immutable policy compiled at play start. The policy contains a context-aware judge, candidate/miss/LN semantics, a compiled gauge definition, effective `TOTAL`, and a versioned descriptor. Live play, the deterministic worker, practice, autoplay, replay, course stages, provenance, and result persistence consume that same policy. The Tachi driver validates recorded LR2 proof before freezing a payload; the SQLite outbox persists only a non-secret ruleset marker and integrity fingerprint and revalidates both before network access.

**Tech Stack:** C++23, SDL2/Yoga views, nlohmann JSON, SQLite, CMake/CTest, existing deterministic gameplay simulation and realtime worker, existing SHA-256 helper, iOS/Android build-only scripts.

## Global Constraints

- Implement only the approved design in `docs/superpowers/specs/2026-07-18-lr2-ruleset-design.md`; do not add LR2IR networking or archive parsing.
- Use pinned LR2 behavior from LR2oraja commit `3db78adff969b854fb3bcc68966449bd36cf7a5b`, LR2oraja 0.8.5 commit `756a537352830c32523fceb6b72ca6416c72a430`, and OpenLR2 commit `aa5500bd331d88d0cc2d81afe52c71939cc896c1`.
- Keep `LR2` and `Beatoraja` as coherent bundles. Ordinary play must not expose independently selectable judge and gauge models.
- Make the persisted profile default `lr2`; do not reinterpret missing or invalid stored attempt provenance as LR2.
- Preserve the existing Beatoraja rank windows, mode-specific gauges, note-priority behavior, course behavior, and default-total formulas bit-for-bit unless an existing test proves the previous behavior was already inconsistent.
- Keep all score-affecting candidate, KPoor, multi-BAD, automatic-POOR, and LN decisions in the authoritative simulation/input transaction path. Rendering must only consume committed results.
- Do not perform string parsing, registry lookup, allocation, JSON work, or virtual dispatch per note in the realtime hot path.
- Do not edit `src/bms_parser.hpp` or `src/bms_parser.cpp`; they are generated amalgamations.
- Never put an API key in provenance, a payload, outbox columns, a fingerprint input, diagnostics, or logs. Credentials remain profile-local and are loaded at request time.
- Existing proof-less IR rows must migrate to a preserved blocked state. Never relabel them LR2, submit them, or delete them automatically.
- Do not deploy. Mobile verification is build-only.
