# bmson Implementation Plan

> **For agentic workers:** Execute with superpowers:executing-plans and test-driven-development.

**Goal:** Load and play legacy bmson 0.21 (also called 0.2.1) and bmson 1.0.

**Architecture:** Implement format decoding in the sibling bms-parser-cpp repository, then regenerate its amalgamation. Version-specific field mapping feeds shared chart timing, notes and resource tables. Synthetic sound IDs describe slices and layers without requiring extracted keysound files.

**Tech Stack:** C++17 parser, C++20 application, vendored JSON reader, existing audio and storage services.

**Spec:** User request; https://bmson-spec.readthedocs.io/en/master/doc/index.html; exch-bms2/jbms-parser; excln/BmsONE legacy conversion.

## Global Constraints

- Parser changes originate in ../bms-parser-cpp, never the generated app copies.
- Preserve file/byte Parse and Scan contracts, cancellation, hashes and existing BMS behavior.
- Discover charts in ordinary folders, archives and Android imports.
- No deployment, worktrees, whole-file formatting, or unrelated edits.

## Review Focus

- Legacy camelCase names and fixed resolution versus modern names and authored resolution.
- Coincident BPM/stop/note events, repeated stops, and continuation slices across tempo changes.
- Shared slices, layered playable notes, long-note pairs and sparse large pulse values.
- Invalid JSON, unsupported versions/modes, null fields and cancellation.
- Consistent slice playback in gameplay, preview, replay and music rendering.
