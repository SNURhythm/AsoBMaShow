# Mobile Gyroscope Turntable Design

## Goal

Expose the built-in motion sensors of iPhone, iPad, Android phones, and Android
tablets as one bindable turntable input. The control uses gyroscope motion fused
with magnetometer-corrected absolute heading, works while the device lies flat,
and establishes a fresh zero heading at the start of every gameplay or practice
attempt. A configurable angular step activates clockwise or counter-clockwise
scratch, and inactivity releases it.

Internet ranking is out of scope.

## User experience

On supported mobile devices, Input settings show one device named **Gyroscope
Turntable** with one semantic axis named **Turntable**. The user binds the
positive and negative directions to Scratch clockwise and Scratch
counter-clockwise through the existing press-to-bind flow. The same stable
logical device identity is used across iOS and Android so an exported input
profile keeps its turntable bindings when moved between supported mobile
devices.

A device-specific settings card exposes:

- **Step angle:** integer degrees from 1 to 45, default 3 degrees.
- **Release delay:** integer milliseconds from 50 to 1000, default 200 ms.

The two scratch directions share these settings. They are not duplicated in
individual bindings because both directions are generated by one physical
heading stream. Existing binding dead-zone and activation/release thresholds
remain unchanged; the processed turntable axis emits full-scale values.

Changes save atomically with the active player's input profile and apply to the
live device immediately after a successful save. A failed save preserves the
previous runtime configuration and shows the existing settings error state.
Applying a successful configuration change releases the axis, discards partial
movement, and establishes a fresh baseline; changing a value can never create
an input transition by itself.

## Beatoraja reference

Beatoraja's current analog scratch version 2 treats its controller axis as a
circular position. It computes a wrap-aware delta, requires deliberate position
movement before activation, refreshes an inactivity counter on movement,
releases after inactivity, and clears its accumulated movement on reversal or
release. The rationale and implementation are documented in:

- [Analog Scratch Revision PR #435](https://github.com/exch-bms2/beatoraja/pull/435)
- [Current controller algorithm](https://github.com/exch-bms2/beatoraja/blob/e6d39ad42c545522897947e72f73a738f0edf45b/src/bms/player/beatoraja/input/BMControllerInputProcessor.java#L414-L491)
- [Mouse scratch version 2](https://github.com/exch-bms2/beatoraja/blob/e6d39ad42c545522897947e72f73a738f0edf45b/src/bms/player/beatoraja/input/MouseScratchInput.java#L263-L351)

Two Beatoraja controller ticks are approximately three degrees of a full
turntable revolution. This design uses that as its default physical step but
uses elapsed milliseconds rather than Beatoraja's controller poll counter. A
completed degree step is already a deliberate movement, so an opposite
completed step reverses direction immediately instead of requiring a second
activation stage.

## Architecture

### Platform motion backends

Add dedicated iOS and Android `IInputBackend` implementations rather than
extending SDL's accelerometer joystick path. Both feed the same C++
heading-to-turntable state machine and publish through the thread-safe
`InputBackendSink` contract. Every registry `pump()` advances the inactivity
clock, even when a platform has not delivered a new sensor sample.

Both platforms publish this fixed snapshot only when their required fused
sensor is supported:

- Stable ID: `builtin:gyroscope-turntable`
- Display name: `Gyroscope Turntable`
- Device class: `Gyroscope`
- Controls: zero buttons, one axis, zero hats

Unsupported hardware publishes no phantom device. The stable identity and
control indices are identical across iOS and Android; platform-native objects
and callbacks never enter the profile format.

#### iPhone and iPad

The Objective-C++ backend owns one `CMMotionManager` and polls the latest
`CMDeviceMotion` sample from the registry's main-thread `pump()`. Polling avoids
callback lifetime and queue-backlog hazards. Only a sample with a newer Core
Motion timestamp is passed to heading processing.

The backend prefers
`CMAttitudeReferenceFrameXArbitraryCorrectedZVertical`. This is an absolute
attitude relative to a stable arbitrary horizontal reference: Z remains world
vertical and Core Motion uses the magnetometer, when available and calibrated,
to correct accumulated yaw error. Magnetic north is unnecessary because each
attempt deliberately establishes its own zero. If that frame is unavailable,
the backend uses `CMAttitudeReferenceFrameXMagneticNorthZVertical`. It must not
advertise a compass-corrected turntable when neither corrected frame is
available.

Read `CMDeviceMotion.attitude.yaw`, not `CMDeviceMotion.heading`: the preferred
arbitrary-corrected frame intentionally has no magnetic-north heading value.
Convert yaw from radians to degrees and normalize it before passing it to the
shared state machine. Set `showsDeviceMovementDisplay` so iOS can request
compass calibration when needed. While
`CMDeviceMotion.magneticField.accuracy` is uncalibrated, the device remains
listed but its axis is released and its heading baseline stays pending. The
first calibrated sample establishes a new baseline without generating input.
Losing calibration during use has the same release-and-reseed behavior.

The iOS target already supports device families 1 and 2, so no iPhone/iPad
deployment-family change is needed. The target links `CoreMotion.framework`,
adds `NSMotionUsageDescription` explaining use on iPhone and iPad, and lists
every new `src` file in the Xcode target membership exceptions required by this
repository. iOS Simulator publishes no device.

#### Android phones and tablets

Add a focused Java `SensorEventListener` manager plus a JNI-backed Android input
backend. The Java manager requires `Sensor.TYPE_ROTATION_VECTOR`, Android's
gyroscope/accelerometer/magnetometer-fused earth-relative orientation sensor.
It must not fall back to `TYPE_GAME_ROTATION_VECTOR`, which omits the
magnetometer, or `TYPE_GEOMAGNETIC_ROTATION_VECTOR`, which omits the gyroscope.
This follows the platform distinction documented by
[Android position sensors](https://developer.android.com/develop/sensors-and-location/sensors/sensors_position).
Because vendors may expose a rotation-vector implementation without a physical
gyro, the backend also requires `Sensor.TYPE_GYROSCOPE`; the feature must not be
advertised as a gyroscope turntable without one.

Register at `SENSOR_DELAY_GAME` on a dedicated `HandlerThread`. Each
`SensorEvent` is converted with `SensorManager.getRotationMatrixFromVector()`
and `SensorManager.getOrientation()`; azimuth is `values[0]` in the range
`[-pi, pi]` about the device's negative Z axis and is normalized to degrees. The
landscape lock and differences in a phone or tablet's natural orientation add
only a constant offset, which the per-attempt baseline removes. The event's
nanosecond timestamp and accuracy accompany the heading through JNI.

`SENSOR_STATUS_UNRELIABLE` is uncalibrated: release the axis and keep the
baseline pending. Low, medium, and high accuracy are accepted, with the first
accepted sample establishing a baseline. Listener callbacks copy the latest
sample into a mutex-protected native slot; only the registry thread mutates the
shared state machine. `stop()` unregisters the listener, terminates its handler
thread, revokes the JNI callback gate, and waits for callbacks to drain. On API
33 and newer, `SensorEvent.firstEventAfterDiscontinuity` forces a release and
new baseline before movement can resume.

The Java manager is owned by `AsoBMaShowActivity`. Activity pause unregisters
the listener and activity resume makes it eligible to restart; native backend
start/stop requests and SDL app lifecycle events converge on the same
idempotent state. Activity destruction performs a final stop even if native
teardown has already run.

Android requires no runtime sensor permission and no high-sampling-rate
permission at `SENSOR_DELAY_GAME`. Add optional, not required, gyroscope,
compass, and accelerometer `<uses-feature>` declarations so Play metadata
describes the capability without excluding devices that cannot use this
optional controller. A device or emulator is published only when both the
rotation-vector and gyroscope default sensors exist and rotation-vector
listener registration succeeds; emulator model strings are not used as a
capability test.

### Heading-to-turntable state machine

A platform-independent C++ state machine owns all signal interpretation. It has
separate operations to observe a fresh
`(headingDegrees, sensorTimestamp, monotonicNow)` sample and to advance a
monotonic inactivity clock. Its output is one of `-1`, `0`, or `+1`. Positive
means clockwise when the device is viewed from above. The native adapters
normalize their signs to this common convention, verified on physical iPhone,
iPad, Android phone, and Android tablet hardware. Binding inversion remains
available to users.

The state contains the previous valid heading, signed unconsumed movement,
active direction, and time of the last completed step.

1. A session reset releases the output, clears partial movement, and marks the
   baseline pending.
2. The first valid sample after a reset establishes the baseline and emits no
   input.
3. Later samples use the shortest signed delta across the 0/360-degree wrap and
   add it to the signed movement accumulator. If the physical delta changes
   sign, any remainder in the old direction is cleared before the new delta is
   added. Opposite movement therefore starts a fresh angular step instead of
   first paying back an old partial step.
4. Reaching at least one positive or negative configured step consumes all
   whole steps, retains only the sub-step remainder, activates that direction,
   and records the current monotonic time as the last completed step.
5. A completed opposite step changes the signed axis directly. The existing
   resolver releases the old scratch direction before pressing the new one in
   the same batch.
6. Advancing the monotonic clock releases an active direction once no complete
   step has arrived for at least the configured release delay. Release also
   clears the partial movement accumulator. Compass jitter therefore cannot
   keep a scratch held merely by producing sub-step motion.

Repeated steps in the current direction refresh the internal deadline without
publishing redundant axis transitions. This behavior is independent of render
frame rate.

### Discontinuity handling

An equal platform sensor timestamp means there is no new sample and is ignored;
it is normal when rendering is faster than sensor delivery. A
non-finite heading or timestamp, a timestamp older than the last observed
sample, a gap over 250 ms between fresh samples, or implied rotation faster
than 1080 degrees per second is a discontinuity. A discontinuity releases the
output and makes the next valid sample a new baseline; it never generates a
scratch. These limits allow much faster movement than a practical mobile-device
turn while rejecting large compass recalibration jumps and resume spikes. The
monotonic inactivity clock continues to release an active direction even when
sensor samples repeat or stall.

On backgrounding, each backend releases the axis, stops its platform sensor,
and clears its baseline without claiming that hardware was unplugged.
Foregrounding restarts sensing and waits for a fresh sample. Duplicate SDL app
and window lifecycle events are idempotent.

While foregrounded, an inactive native sensor, no first sample within one
second of startup, or no newer sample for one second is a sensor failure. The
backend releases the axis, publishes a disconnected snapshot, stops sensing,
and schedules another start attempt after two seconds. A fresh sample of any
calibration accuracy republishes the connected snapshot; only a calibrated
sample establishes the heading baseline, and it does so without input. Retries
stop while the app is backgrounded and resume on the next foreground
transition.

## Session lifecycle

`GamePlayScene::reset()` is the canonical attempt boundary. It runs for initial
gameplay, Chart Viewer practice, same-pattern retries, result retries, course
stages, and retry recovery.

At the beginning of a same-scene reset, the registry resets the gyroscope
turntable session and synchronously dispatches its zero-axis release before
gameplay state is torn down. This clears the held scratch direction without
resetting unrelated keyboard, controller, touch, or MIDI input. Initial scene
setup performs the same registry reset before the gameplay input handler
subscribes. The backend then keeps its heading baseline pending; no heading from
a previous attempt may be reused when a fresh sample is temporarily
unavailable.

Settings monitoring uses the same state machine but is not a gameplay session.
It starts from a backend-start or foreground baseline so a user can rotate the
device to capture and test both directions. Starting gameplay always discards
that settings-session state.

## Profiles and provenance

Add one shared configuration object to `InputProfile`:

```json
"gyroscopeTurntable": {
  "stepAngleDegrees": 3,
  "releaseDelayMs": 200
}
```

Bump the input-profile schema from version 1 to version 2. Version 1 profiles
migrate by preserving every binding and adding the default gyroscope settings.
Missing or invalid version 2 values recover independently to their defaults and
produce diagnostics. Well-typed integer values outside the supported ranges are
clamped to the nearest boundary during normal sanitization. Future versions
remain rejected.

Add `DeviceClass::Gyroscope` and serialize it as `"gyroscope"`. Do not classify
the device as a joystick: its identity, settings label, binding persistence,
and score provenance should remain truthful. Append a Gyroscope score input
category without renumbering existing categories. Bump score provenance to
version 2 for the expanded device vocabulary. Version 1 provenance migrates
without changing any existing field or device name; unknown future versions
remain rejected.

The application applies the active input profile's gyroscope configuration to
the long-lived registry at startup, after a successful Input settings save, and
after an active-profile replacement. A failed profile load or switch retains
the already-active runtime configuration. Every successful runtime
configuration replacement releases and re-baselines the turntable before using
the new values.

## Data flow

```text
iOS CMMotionManager attitude.yaw ─┐
                                  ├─> mobile gyroscope backend
Android TYPE_ROTATION_VECTOR ─────┘
  -> shared heading turntable state machine
  -> Axis 0 (-1 / 0 / +1)
  -> InputDeviceRegistry
  -> InputBindingResolver
  -> clockwise/counter-clockwise scratch actions
  -> LogicalGameplayInputAdapter
```

No change is required to chart parsing, judgement, replay input recording, or
scratch-lane semantics. Existing axis direction binding and atomic reversal
ordering are reused.

## Testing

Implementation proceeds test-first.

Pure C++ state-machine tests cover:

- first-sample and explicit-session baseline behavior;
- clockwise and counter-clockwise step activation;
- accumulation of sub-step movement and whole-step remainder;
- 359-to-0 and 0-to-359 wraparound;
- same-direction deadline refresh;
- full opposite-step reversal ordering;
- timeout release and partial-movement clearing;
- equal timestamps with independent timeout advancement;
- invalid numbers, older timestamps, long gaps, and implausible jumps;
- loss and recovery of magnetometer calibration;
- sensor-stall disconnect, timed retry, and reconnect ordering;
- background/foreground and retry reseeding;
- configuration boundary values and active-state replacement.

Backend and registry tests use an injected fake motion source to cover device
availability, iOS Simulator absence, Android reported-sensor capability,
connect-before-input ordering, one semantic axis, configuration updates,
idempotent stop, background release, callback-after-stop safety, and restart.
Pure Java tests cover azimuth-radians-to-heading normalization for 0,
positive/negative 90-degree, and wraparound cases, plus lifecycle and
calibration policy without Android framework mocks. The thin calls to
`SensorManager` are compile-checked by the Android build.
Profile tests cover version 1 migration, version 2 round-trip, sanitization,
future-version rejection, and the new device class. Provenance tests cover the
Gyroscope category without changing existing category values. Settings tests
cover compact phone layout, card visibility, units, save failure behavior, and
the semantic Turntable label.

Verification includes focused CTests, the full CTest suite, the desktop `main`
build, Android JVM tests, `git diff --check`,
`scripts/ios_firebase_deploy.sh --build-only`, and
`scripts/android_firebase_deploy.sh --build-only --variant playDebug`. Build-only
commands must not upload a build.

Final sensor acceptance requires physical mobile hardware because iOS Simulator
cannot validate Core Motion and Android emulator sensor availability varies.
Test at least one iPhone, iPad, Android phone, and Android tablet. In both
landscape orientations with the device screen-up and flat on a table, test slow
and fast turns in both directions, repeated full rotations across north/wrap,
rest noise, magnetic cases or accessories, calibration changes, direction
reversal, retry/practice reset, and background/foreground release.

## Acceptance criteria

- Supported iPhone, iPad, Android phone, and Android tablet hardware exposes one
  clearly named Gyroscope input device with the same persistent identity.
- The device can bind its two directions to clockwise and counter-clockwise
  scratch through the existing settings flow.
- A 3-degree turn activates by default, and step angle is adjustable in degrees.
- The scratch releases 200 ms after the last completed step by default, and the
  delay is adjustable in milliseconds.
- Resting sub-step sensor noise does not activate or prolong scratch, and
  rejected heading discontinuities never generate input.
- Heading is reset for every gameplay, practice, retry, and course attempt.
- Flat-table rotation works through magnetometer-corrected, world-vertical
  attitude.
- Unsupported devices and iOS Simulator show no false connected device;
  Android relies on reported sensor capability rather than emulator identity.
- Existing profiles, bindings, input devices, scores, and scratch behavior
  remain compatible.
